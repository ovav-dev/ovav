# F2: enable_csi_u_key_encoding behavior in 2026 nightly

## Findings

### [1] enable_csi_u_key_encoding default is false and has NOT changed
The config option `enable_csi_u_key_encoding` defaults to `false` in current WezTerm. The official docs (wezterm.org) and the GitHub main-branch source file both state: "The default for this option is `false`." There is no evidence in any official documentation of this default changing in 2026 nightly.
- quote: "The default for this option is `false`."
- url: https://wezterm.org/config/lua/config/enable_csi_u_key_encoding.html
- source_type: primary
- published: unknown (current docs, repo commit history not showing recent change)
- confidence: high

### [2] enable_csi_u_key_encoding is NOT deprecated
The option is present in the current GitHub main-branch source (last commit on the file shows no deprecation marker). The docs page for `enable_csi_u_key_encoding` is alive and linked from the config index. No deprecation notice appears anywhere in official docs.
- quote: "# `enable_csi_u_key_encoding = false`"
- url: https://github.com/wez/wezterm/blob/main/docs/config/lua/config/enable_csi_u_key_encoding.md
- source_type: primary
- published: unknown
- confidence: high

### [3] The option is explicitly NOT recommended
The official documentation carries a strong warning: "It is not recommended to enable this option as it does change the behavior of some keys in backwards incompatible ways and there isn't a way for applications to detect or request this behavior." This language has been stable and is unchanged.
- quote: "It is not recommended to enable this option as it does change the behavior of some keys in backwards incompatible ways and there isn't a way for applications to detect or request this behavior."
- url: https://wezterm.org/config/lua/config/enable_csi_u_key_encoding.html
- source_type: primary
- published: unknown
- confidence: high

### [4] allow_win32_input_mode takes precedence over enable_csi_u_key_encoding (unchanged)
Both the `enable_csi_u_key_encoding` docs and the `allow_win32_input_mode` docs confirm that on Windows, `allow_win32_input_mode` (which defaults to `true`) takes precedence. This precedence relationship is documented and unchanged.
- quote: "Note that allow_win32_input_mode takes precedence over this option."
- url: https://wezterm.org/config/lua/config/enable_csi_u_key_encoding.html
- source_type: primary
- published: unknown
- confidence: high

### [5] The Kitty Keyboard Protocol (enable_kitty_keyboard) is the actively maintained alternative
`enable_kitty_keyboard` was introduced in version 20220624-141144-bd1b7c5d (June 2022) as a more feature-rich alternative to CSI-u. It allows applications to request encoding changes via escape sequences. The changelog notes: "Support for the Kitty Keyboard Protocol. Use enable_kitty_keyboard=true to enable it." CSI-u predates and is superseded by the Kitty protocol for new use cases.
- quote: "When set to true, wezterm will honor kitty keyboard protocol escape sequences that modify the keyboard encoding."
- url: https://wezterm.org/config/lua/config/enable_kitty_keyboard.html
- source_type: primary
- published: unknown
- confidence: high

### [6] The underlying CSI-u/fixterms scheme has known issues acknowledged in official docs
The keyboard encoding docs reference that the fixterms scheme (which CSI-u implements) "is not a perfect attempt as there are a number of issues with it" — linking to Kitty's own bug documentation at sw.kovidgoyal.net. This provides context for why the option is discouraged.
- quote: "It's not a perfect attempt as there are a number of issues with it"
- url: https://wezterm.org/config/key-encoding.html
- source_type: primary
- published: unknown
- confidence: high
