# F5: OpenCode extensions and external integrations

## Findings

### [1] OpenCode ships native MCP (Model Context Protocol) support for both local stdio-based and remote HTTP servers, with full OAuth auto-detection and per-agent granularity
OpenCode's MCP implementation supports local servers started as child processes (`type: "local"`, `command: ["npx", "-y", "..."]`) and remote servers via HTTP (`type: "remote"`, `url: "https://..."`). For remote servers, OpenCode automatically handles OAuth 2.0 Dynamic Client Registration (RFC 7591), detects 401 responses and initiates the auth flow, and stores tokens in `~/.local/share/opencode/mcp-auth.json`. MCP servers can be enabled/disabled globally via `tools` config or per-agent via agent-level `tools` overrides using glob patterns (e.g., `my-mcp*`). Org-level defaults can be pushed via a `.well-known/opencode` endpoint, with servers shipped disabled-by-default for user opt-in. The documented example integrations include Sentry (OAuth), Context7 (API key via header), and Grep by Vercel.
- quote: "OpenCode supports both local and remote servers... MCP servers are automatically available to the LLM alongside built-in tools."
- url: https://opencode.ai/docs/mcp-servers/
- source_type: primary
- published: Aug 6, 2026
- confidence: high

### [2] OpenCode's plugin system exposes 30+ event hooks for extending behavior, including tool execution, session lifecycle, file watching, LSP diagnostics, shell environment, and TUI controls
Plugins are JavaScript/TypeScript modules that export a function receiving `{ project, client, $, directory, worktree }` and return a hooks object. Available hook categories include: `tool.execute.before/after`, `shell.env` (inject env vars into all shell execution), `session.created/updated/compacted/deleted/idle/error`, `file.edited`, `file.watcher.updated`, `lsp.client.diagnostics`, `lsp.updated`, `permission.asked/replied`, `tui.prompt.append`, `tui.command.execute`, `tui.toast.show`, `installation.updated`, `command.executed`, `message.removed/updated`, `server.connected`, `todo.updated`, and experimental `session.compacting` for customizing context summarization. Plugins are loaded from `.opencode/plugins/` (project), `~/.config/opencode/plugins/` (global), or npm packages listed in config. Custom tools can also be exported from plugins using the `tool()` helper with Zod schema validation.
- quote: "Plugins allow you to extend OpenCode by hooking into various events and customizing behavior."
- url: https://opencode.ai/docs/plugins/
- source_type: primary
- published: Aug 6, 2026
- confidence: high

### [4] OpenCode implements the open Agent Client Protocol (ACP), enabling integration with Zed, JetBrains IDEs, Avante.nvim, and CodeCompanion.nvim
OpenCode's ACP support is activated via `opencode acp`, which starts the agent as a JSON-RPC subprocess communicating over stdio. ACP is an open protocol (agentclientprotocol.com) that standardizes editor-to-agent communication. Zed integration uses `agent_servers` config with `opencode acp` command; JetBrains uses `acp.json` with an absolute binary path; Avante.nvim uses `acp_providers` config map; CodeCompanion.nvim uses the adapter pattern with `opencode` as adapter name. Full feature parity is advertised: built-in tools, custom tools, MCP servers, AGENTS.md rules, formatters, agents, and permissions all work via ACP, with only `/undo` and `/redo` as current exceptions.
- quote: "OpenCode supports the Agent Client Protocol (ACP), allowing you to use it directly in compatible editors and IDEs."
- url: https://opencode.ai/docs/acp/
- source_type: primary
- published: Aug 6, 2026
- confidence: high

### [5] The `@opencode-ai/sdk` npm package provides a full TypeScript client for programmatic control of OpenCode sessions, with an OpenAPI 3.1 spec published by the server
The SDK (`npm install @opencode-ai/sdk`) exposes: `createOpencode()` to spawn both server and client, `createOpencodeClient()` to attach to an existing server at `http://localhost:4096`. Full session management API includes `session.create/prompt/list/delete/update/share/revert/unrevert/abort/fork/summarize`, file operations (`file.read`, `find.text/files/symbols`), TUI control (`tui.appendPrompt/submitPrompt/showToast`), structured output via JSON schema with retry logic, and an SSE event stream via `event.subscribe()`. The server (`opencode serve`) publishes its OpenAPI 3.1 spec at `/doc` and supports mDNS discovery, HTTP basic auth (`OPENCODE_SERVER_PASSWORD`), and CORS configuration. An experimental `/experimental/tool/ids` and `/experimental/tool` endpoint exposes tool schemas per model.
- quote: "The opencode JS/TS SDK provides a type-safe client for interacting with the server."
- url: https://opencode.ai/docs/sdk/
- source_type: primary
- published: Aug 6, 2026
- confidence: high

### [6] Agent Skills are on-demand-loaded SKILL.md definitions discoverable from repo, home directory, or Claude-compatible paths, with per-skill permission controls
Skills are `.opencode/skills/<name>/SKILL.md` (project), `~/.config/opencode/skills/<name>/SKILL.md` (global), or Claude-compatible `.claude/skills/<name>/SKILL.md` and `.agents/skills/<name>/SKILL.md`. Skills are loaded lazily via the native `skill` tool — the LLM sees available skills in its context and calls `skill({ name: "..." })` to load full content. SKILL.md files require YAML frontmatter with `name` and `description` (1-1024 chars). Permissions are pattern-based in `opencode.json` with `allow/deny/ask` per skill name pattern (e.g., `"internal-*": "deny"`, `"pr-review": "allow"`), overridable per-agent in agent frontmatter. Skills are compatible with OpenCode's own format as well as Claude's skill format.
- quote: "Agent skills let OpenCode discover reusable instructions from your repo or home directory. Skills are loaded on-demand via the native `skill` tool."
- url: https://opencode.ai/docs/skills/
- source_type: primary
- published: Aug 6, 2026
- confidence: high

### [7] Custom Tools are defined as TypeScript/JavaScript files in `.opencode/tools/` or `~/.config/opencode/tools/` and can invoke scripts in any language via Bun shell utilities
Tool definitions use the `tool()` helper from `@opencode-ai/plugin` with Zod schema args, filename becoming the tool name. Multiple tools per file are exported as `<filename>_<exportname>`. Custom tools take precedence over built-in tools with the same name. Tools receive a `context` object with `{ agent, sessionID, messageID, directory, worktree }`. The example shows a Python script invoked via `Bun.$` backticks from within a TypeScript tool definition, demonstrating polyglot tool execution. Tools can be placed in local (`.opencode/tools/`) or global (`~/.config/opencode/tools/`) directories.
- quote: "Tools are defined as TypeScript or JavaScript files... the tool definition can invoke scripts written in any language."
- url: https://opencode.ai/docs/custom-tools/
- source_type: primary
- published: Aug 6, 2026
- confidence: high

### [8] OpenCode Enterprise supports centralized org-level config for MCP defaults, SSO integration, internal AI gateway enforcement, and private NPM registry usage
Enterprise deployment is per-seat pricing with the option to self-host share pages (roadmap). Central config via `.well-known/opencode` allows orgs to push default MCP server configurations with opt-in rather than opt-out semantics. SSO integration is available through the central config mechanism. All LLM providers can be disabled in favor of an internal AI gateway only. Private NPM registries (JFrog Artifactory, Nexus, etc.) are supported via Bun's native `.npmrc` with `npm login --registry=...` before running OpenCode. Self-hosting of share infrastructure is documented as on the roadmap.
- quote: "With the central config, OpenCode can also be configured to use only your internal AI gateway. You can also disable all other AI providers."
- url: https://opencode.ai/docs/enterprise/
- source_type: primary
- published: Aug 6, 2026
- confidence: high

### [10] OpenCode's headless server mode exposes an OpenAPI 3.1 spec and supports programmatic session injection, MCP dynamic addition, and SSE event streaming
`opencode serve` starts an HTTP server (default `127.0.0.1:4096`) with a published OpenAPI 3.1 spec at `/doc`. Key server APIs include `POST /session/:id/message` (send prompt and wait for response), `POST /session/:id/prompt_async` (fire-and-forget), `POST /mcp` (dynamic MCP server addition without restart), `GET /mcp` (MCP server status), `POST /tui/*` (drive TUI programmatically: append-prompt, submit-prompt, show-toast, execute-command), `GET /tui/control/next` and `POST /tui/control/response` for interactive TUI control, and `GET /event` for SSE event stream. The server supports mDNS discovery (`--mdns` flag) for zero-config network service announcement.
- quote: "The server exposes an OpenAPI 3.1 spec endpoint... Use the opencode server to interact with opencode programmatically."
- url: https://opencode.ai/docs/server/
- source_type: primary
- published: Aug 6, 2026
- confidence: high

## Dead ends
- No specific mention of a native OpenCode "app store" or marketplace for extensions; ecosystem is documented as a static list with PR-submission workflow
- No mention of GraphQL or gRPC transport for MCP; only stdio (local) and HTTP+SSE (remote) are documented
- No mention of Helm charts, Kubernetes operators, or container-native deployment primitives beyond Docker binary
- No mention of native SIEM/SOAR platform connectors (Splunk, PagerDuty, etc.) beyond Sentry and JFrog
- The `.well-known/opencode` central config mechanism for enterprise MCP defaults was referenced but its full schema was not publicly documented
