# F3: Observability (logs, events, webhooks)

## Findings

### [1] JSON Event Stream Mode exposes a comprehensive, structured event stream of all agent lifecycle, tool calls, and governance events as JSON Lines to stdout
- quote: "Outputs all session events as JSON lines to stdout. Useful for integrating pi into other tools or custom UIs."
- url: https://pi.dev/docs/latest/json
- source_type: primary
- published: unknown
- confidence: high

### [2] The JSON event stream includes granular tool-level observability: tool_execution_start, tool_execution_update (with partial results), and tool_execution_end events carrying toolCallId, toolName, args, and result
- quote: "tool_execution_end: { toolCallId: string, toolName: string, result: any, isError: boolean }"
- url: https://pi.dev/docs/latest/json
- source_type: primary
- published: unknown
- confidence: high

### [3] The event stream includes separate agent lifecycle events: agent_start, agent_end (with full messages array), and agent_settled (fires only when no automatic retry, compaction, or queued follow-up remains)
- quote: "agent_settled: Agent run is fully settled; no automatic retry, compaction retry, or queued continuation remains"
- url: https://pi.dev/docs/latest/rpc
- source_type: primary
- published: unknown
- confidence: high

### [4] RPC Mode exposes a bidirectional JSON protocol over stdin/stdout with command/response framing plus server-push event streaming, including get_session_stats returning per-session token counts, cost, and context window utilization
- quote: "get_session_stats returns: tokens: { input, output, cacheRead, cacheWrite, total }, cost, contextUsage: { tokens, contextWindow, percent }"
- url: https://pi.dev/docs/latest/rpc
- source_type: primary
- published: unknown
- confidence: high

### [5] The SDK exposes AgentSession.subscribe() for in-process programmatic event consumption with identical event taxonomy to JSON/RPC modes, including tool execution, turn lifecycle, compaction, and retry events
- quote: "session.subscribe((event) => { switch (event.type) { case 'tool_execution_start': ... case 'tool_execution_end': ... case 'agent_start': ... case 'agent_end': ... }})"
- url: https://pi.dev/docs/latest/sdk
- source_type: primary
- published: unknown
- confidence: high

### [6] Extensions can subscribe to before_provider_request and after_provider_response events, enabling HTTP-level observability including header mutation and response status/header inspection before stream consumption
- quote: "before_provider_request: Fired after the provider-specific payload is built, right before the request is sent. after_provider_response: Fired after an HTTP response is received and before its stream body is consumed."
- url: https://pi.dev/docs/latest/extensions
- source_type: primary
- published: unknown
- confidence: high

### [7] The tool_call extension event is interceptable — extensions can block or modify tool calls before execution, inspect/modify args, and log decisions; no native webhook exists, but extensions can implement arbitrary HTTP calls
- quote: "tool_call: Fired after tool_execution_start, before the tool executes. Can block. Return { block: true, reason?: string, terminate?: boolean }"
- url: https://pi.dev/docs/latest/extensions
- source_type: primary
- published: unknown
- confidence: high

### [8] Compaction events (compaction_start, compaction_end) fire for both manual and automatic compaction, exposing token counts before/after, estimated cost, and the compaction reason (manual, threshold, overflow)
- quote: "compaction_end: { reason, result: { summary, firstKeptEntryId, tokensBefore, estimatedTokensAfter, usage: { input, output, cacheRead, cacheWrite, totalTokens, cost } }, aborted, willRetry }"
- url: https://pi.dev/docs/latest/rpc
- source_type: primary
- published: unknown
- confidence: high

### [9] Session files are stored as JSONL with complete message history (user, assistant, toolResult, bashExecution), enabling post-hoc replay and audit; the session format includes tree structure with parent/child entry linking and stable entry IDs
- quote: "Session Format: JSONL session file format, entry types, and SessionManager API."
- url: https://pi.dev/docs/latest/session-format
- source_type: primary
- published: unknown
- confidence: high

### [10] Bash command execution streams output in real-time via bash_execution_update events with delta chunks, and the final response includes fullOutputPath for truncated output and exitCode
- quote: "bash_execution_update: Emitted once for each output chunk from a direct bash command. id matches the command's id. Events stream all output while the command runs, even if the final output is truncated."
- url: https://pi.dev/docs/latest/rpc
- source_type: primary
- published: unknown
- confidence: high

### [11] Auto-retry events (auto_retry_start, auto_retry_end) expose transient error details including attempt number, maxAttempts, delayMs, and errorMessage, enabling monitoring of reliability patterns
- quote: "auto_retry_start: { attempt, maxAttempts, delayMs, errorMessage }"
- url: https://pi.dev/docs/latest/rpc
- source_type: primary
- published: unknown
- confidence: high

### [12] Queue update events (queue_update) expose pending steering and follow-up message queues in real-time, showing pending governance interventions before they reach the LLM
- quote: "queue_update: Emitted whenever the pending steering or follow-up queue changes. { steering: string[], followUp: string[] }"
- url: https://pi.dev/docs/latest/rpc
- source_type: primary
- published: unknown
- confidence: high

## Dead ends
- "pi.dev webhook" — no webhook documentation exists; the platform provides events and an extension API, but no native webhook dispatch mechanism
- "pi.agent monitoring integration datadog" — no Datadog, OpenTelemetry, or APM integrations found in official docs
- "pi.dev logging external" — no dedicated logging export format (no structured log forwarding like JSON+syslog); session JSONL files are the persistence layer
- "pi.dev governance events audit" — no dedicated governance/audit log endpoint; governance events (tool blocks, compaction, retry) are observable only through the general event stream

## Suggested follow-ups
- Can an extension intercept and forward events to an external HTTP endpoint (webhook)? The extension docs mention "External integrations (file watchers, webhooks, CI triggers)" as an example use case, but no built-in webhook primitive exists — an extension would need to implement its own HTTP call.
- Does pi expose an OpenTelemetry-compatible trace/span model? The events cover the operational surface, but no OTEL SDK or compatibility layer is documented.
- What is the complete set of event types available in the JSON stream vs. the RPC stream? Both document similar events, but a diff is not provided.
