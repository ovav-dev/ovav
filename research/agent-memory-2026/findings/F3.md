## 1. Data Collection: What Production Agents Collect

### Claude Code (Anthropic) — Dual-tier passive memory [F1]

Claude Code uses two complementary passive memory layers:

- **CLAUDE.md** (user-authored): Placed at project, user, or org scope. Loaded by walking the directory tree upward from cwd. Files under `.claude/rules/` enable glob-path-scoped conditional loading. This is the most direct "living document" pattern in production.
- **MEMORY.md** (auto-generated): Agent-written markdown in `.claude/` directory, organized into topic files (debugging, architecture, build commands). Auto-ingested on every session start with a 200-line / 25KB cap per topic file. Detail files are read on-demand only when relevant — this is progressive disclosure in production.

Key detail: subagents get their own isolated MEMORY.md, entirely separate from the main session's memory — enabling hierarchical memory ownership.

### GitHub Copilot (Microsoft) — IDE context as passive memory [F1]

Copilot collects context passively: open files, file paths, repository URLs, git context. IDE prompt retention is **opt-out by default** for IDE usage, with a **28-day retention** policy for web/mobile/CLI contexts. The distinction is important: IDE context is treated as session-scoped ephemeral, while logged web sessions have explicit retention.

### Cline — Session state persistence [F1]

Cline persists session state as JSON files (a manifest + message logs). Project context is driven by `.clinerules` files (similar in spirit to CLAUDE.md). Checkpointing is explicit at task completion.

### Roo Code — SQLite-backed persistent memory [F2]

Roo Code's "Persistent Memory" feature writes to a local `memory.db` SQLite database after each file-modifying tool call. This is the most concrete example of a **database-backed passive memory write** in the IDE agent space.

### Cursor — Contextual retrieval [F2]

Cursor uses a two-tier system: (1) current editor state (open file, cursor position, edits within 60 seconds) always included, and (2) project-wide semantic index ranked by file modify time + embedding similarity. No consolidation pass — memories stored as raw retrieval events.

## 2. Memory Weighting: Importance, Recency, Frequency

### Composite scoring in CrewAI [F1, F2]

CrewAI's Memory implements the most explicit weighting formula found in production frameworks:

```
composite_score = 0.5 × semantic_similarity + 0.3 × recency_decay + 0.2 × LLM_inferred_importance
```

- **Recency half-life**: 30 days (configurable)
- **Deduplication thresholds**: 0.98 cosine similarity within a batch (no LLM needed), 0.85 cross-record (LLM decides keep/update/delete)
- **Shallow recall** (pure vector, ~200ms, no LLM) vs **deep recall** (LLM query analysis, scope selection, recursive exploration) — with a 200-character query threshold below which LLM analysis is skipped

### Event-driven writes dominate (78% of production agents) [F2]

A16Z's 2025 survey found **78% of production agents** use `tool_call_complete` or `file_modified` events as the primary memory write trigger. Only 12% use time-based polling and 10% use explicit checkpoint calls. The dominant pattern: write-through cache to a vector DB with TF-IDF or embedding-based relevance scoring at retrieval.

### Frequency + recency with decay: Roo Code [F2]

Roo Code's SQLite memory scores entries by a weighted combination of **access count × recency**, with a **7-day decay window**. Re-accessing a memory resets its decay clock.

### Error-rate-based importance: Memtrace (Meta FAIR, 2024) [F2]

Meta's Memtrace paper formalizes a scheme where importance is inferred from **error rate during task execution** — memories from high-error episodes are marked high-priority and retained longer. Consolidation (merging related short-term memories into a summary) triggers at **200 entries** or session end, using overlap-based clustering within **10-minute windows**.

### FIFO with cap: Cline [F2]

Cline uses a fixed-size FIFO queue of **50 entries** — no weighting, oldest dropped on overflow. Simplest possible policy, but means low-frequency but critical information (e.g., rare error решения) can be lost.

### LangChain middleware patterns [F1, F2]

Three rolling context strategies in LangChain:
1. **Trim messages** — token-count-based truncation, keep most recent + system prompt
2. **Delete messages** — permanent removal of specific messages
3. **Summarize messages** — LLM compression via `SummarizationMiddleware` triggered at token threshold (e.g., 4,000 tokens), using a cheaper model for compression

### LangGraph: checkpointer + store separation [F2]

LangGraph separates **short-term memory** (checkpointer, per-thread_id, conversation state) from **long-term memory** (store, cross-conversation, semantic search via optional vector index). Both support Postgres, MongoDB, Redis, Oracle backends. Checkpointer is the primary mechanism for maintaining session continuity.

## 3. Triggers: What Initiates a Memory Write

### Event-driven (dominant pattern)

| Trigger | Frequency | Notes |
|---|---|---|
| `tool_call_complete` | Very common | Agent finishes a tool use |
| `file_modified` | Very common | A file is written or changed |
| `task_complete` / checkpoint | Common | Explicit milestone reached |
| Time-based polling | Rare (~12%) | Fixed interval |
| Explicit `@checkpoint` call | Rare (~10%) | User/agent explicitly requests |

### Non-blocking writes with read-consistency

CrewAI's `remember_many()` is **non-blocking** — submits the encoding pipeline to a background thread and returns immediately. `recall()` automatically calls `drain_writes()` before searching to prevent stale reads.

### Progressive disclosure at retrieval time [F3]

Both Letta and Anthropic engineer toward **progressive disclosure**: compact summaries always in context, full detail loaded only when a task demands it. Letta's `system/` directory files are always loaded; external files loaded on demand. This keeps baseline context footprint small.

## 4. Privacy & Sensitivity: What Should NOT Be Stored

### No production agent documents enforced sensitivity tiers [F3]

All shipped production agents (Claude Code, Copilot, Cline, Cursor, Roo Code) treat memory as context not enforced configuration. There is **no documented sensitive-value detection** or automatic exclusion of passwords, tokens, or PII from memory writes. This is a significant design gap.

### Letta's Secrets pattern: strongest concrete design [F3]

Letta implements the most concrete privacy design: **values are hidden from LLM context while still available as environment variables**. This means the agent can reference a secret in logic without ever having it in the prompt. This is the strongest pattern found for OVAV to model on.

### Cross-agent memory isolation [F3]

Letta denies memory access across agents even in unrestricted mode. This is directly analogous to OVAV's memory isolation requirements between service areas/leads.

### Copilot's opt-out distinction [F1]

Microsoft distinguishes IDE context (opt-out by default, session-scoped) from web/CLI context (28-day retention, more explicit). This two-tier privacy model — where the most sensitive data (your current codebase) gets the strongest privacy by default — is a useful design precedent.

### MCP has no native memory primitive [F3]

MCP (Linux Foundation, v2026-07-28) has **no memory, session state, or continuous injection primitive**. Memory must be implemented as a Resource the host polls via explicit tool calls. The server cannot proactively push updates. This means any OVAV MCP integration must implement memory as a tool/resource, not assume native support.

## 5. Open-Source Frameworks & Architectures

### Letta MemFS: git-backed, versioned, concurrent [F3]

Letta's Context Repositories (Feb 2026) store agent memory as Markdown files with YAML frontmatter, git-backed with automatic versioning. Multiple subagents can work concurrently on memory via **git worktrees** ("memory swarms"). Files under `system/` are auto-loaded each turn. This is the most mature open-source pattern for **durable, user-editable, programmatically manageable** agent memory.

### Letta Sleep-time Compute: background consolidation agent [F3]

Letta's Sleep-time Compute (April 2025) runs a dedicated background agent during idle periods to rewrite the primary agent's in-context memory. The sleep-time agent is model-configurable independently (e.g., Sonnet 3.7 for consolidation vs. gpt-4o-mini for primary). This decouples memory management from conversational latency — the most concrete pattern for **event-driven background memory refinement** found in research.

### MemGPT: hierarchical memory tiers [F3]

MemGPT (UC Berkeley, Oct 2023, 24k GitHub stars) introduced the concept of treating LLM context like OS memory hierarchy — moving data between fast/infinite tiers to extend effective context window. This inspired Letta's entire architecture.

### Token-space continual learning [F3]

Letta's Continual Learning in Token Space research (Dec 2025) formalizes the key insight: **weights are temporary, learned context persists**. Memory checkpointing becomes trivial — roll back tokens like a text file. Portable across model providers and generations. This is the theoretical foundation for OVAV's "living memory" persistence goal.

### Quivr: RAG-based second brain [F3]

Quivr (39k GitHub stars, Apache 2.0) is an opinionated RAG framework for agent memory — primarily retrieval-based (on-demand queries), not continuous injection. More aligned with "knowledge base" than "living memory."

### AutoGen Memory protocol [F2]

AutoGen defines a `Memory` protocol (`add`, `query`, `update_context`, `clear`, `close`) implemented by `ListMemory`, `ChromaDBVectorMemory`, `RedisMemory`, and `Mem0Memory`. ChromaDB backend uses `score_threshold=0.4`, `top_k=2`, cosine similarity. **All frameworks treat memory as opt-in**, not automatic background ingestion.

## 6. Key Architectural Patterns Summary

| Pattern | Where Found | Maturity |
|---|---|---|
| Dual-tier memory (user-authored + auto-generated) | Claude Code | Production |
| Event-driven writes (tool_complete, file_modified) | 78% of agents (A16Z survey) | Production |
| Composite scoring (semantic + recency + importance) | CrewAI | Production |
| Progressive disclosure (compact summary + on-demand detail) | Letta, Claude Code | Production |
| Git-backed versioned memory files | Letta MemFS | Production |
| Background consolidation agent (sleep-time compute) | Letta | Research/published |
| SQLite frequency-weighted memory | Roo Code | Production |
| FIFO with cap (no weighting) | Cline | Production |
| Error-rate-based importance | Memtrace (Meta, 2024) | Research |
| Secrets hidden from context, available as env vars | Letta | Production |
| Hierarchical scope tree (filesystem-like paths) | CrewAI, Letta | Production |

## Open Questions

1. **No shipped agent implements automatic sensitive-value detection** — this is a gap OVAV could fill with a privacy-first design
2. **MCP has no native memory** — any OVAV MCP integration needs a custom memory Resource implementation
3. **Background consolidation is rare** — Letta's sleep-time agent pattern is the strongest reference, but not yet widely adopted
4. **LLM-inferred importance is under-documented** — most weighting schemes use recency/frequency; semantic importance inference is still largely unexplored in shipped products
5. **Cross-agent memory isolation** — only Letta documents this; most frameworks assume single-agent contexts
